1. **Read the transcript** at the `transcript` path. It is JSONL — one record per line. It includes the human turns *and* any sidechain subagent work (`"isSidechain":true`) spawned during the session. Treat subagent output as **source material to fold in**, never as a separate entry. If the header's `already_summarized_through` is a real timestamp (not `none`), focus on transcript lines whose ISO-8601 `timestamp` string sorts *after* it — the earlier part is already in the wiki; if it is `none`, read the whole transcript. **If the transcript is large (more than ~1500 lines / ~400KB), do not read it whole** — read the first ~200 and last ~400 lines and sample the middle; you need the arc, decisions, and findings, not every token.

2. **Judge worthiness.** If this segment produced no durable knowledge — trivial Q&A, throwaway commands, an abandoned false start, or pure mechanical edits with no decision or finding — then **do not create or edit any wiki page**. A session that produced only prep, planning, scaffolding, or "next step is …" notes with no durable decision or finding is **not** page-worthy: at most append a single dated bullet to the most relevant existing page's session list — never create a new page for it.

3. **Find any existing wiki coverage of this work BEFORE writing — extending beats duplicating.** Two sources, in order: (a) **`prior_project_pages`** in the header is the deterministic anchor — it lists every page the wiki already holds for *this project*, built from earlier runs. **Open and read each one first**; if any covers what this segment worked on, that page is your target. (`prior_wiki_pages` is the same idea but keyed to this one session id — usually empty, since a returning session launches with a new id, so do not rely on it.) (b) If `prior_project_pages` is empty or none of them fit, **search** for an existing home: read `wiki/index.md` and the relevant `wiki/<domain>/_index.md`, `Glob` the likely folder (e.g. `wiki/codebases/` for a code project), and `Grep` the wiki for the `project` path/name and key entities (file names, system names, functions) from the transcript. If a page already covers this project/topic, this is a **continuation**: **extend that page** — append/refine sections, bump its `updated` frontmatter, add a dated note — and do **not** create a duplicate, a `-2` variant, or re-state what it already says. Only **create a new page** when the work is a genuinely new topic with no existing home; then cross-link it to related pages with `[[wikilinks]]` in both directions. The prior page's *text* (not a timestamp gap) tells continuation from spin-off. When unsure, prefer extending over fragmenting. **Page-vs-section & naming (hard rules):** one topic = one page, and a *session* is never a topic. CREATE a new page only for a self-contained, named reference artifact a future unrelated session would seek out *by name* (e.g. a distinct architecture or design audit with its own internal structure). FOLD everything else into the project's anchor page as a dated section or bullet — session work-logs, "what we did", prep/planning, and status snapshots. **Never name a page with a date prefix (`2026-06-12-…`) or after a session** — dates belong in `created`/`updated` frontmatter, not filenames; page names are topic names (e.g. `sector-collision-system`, not `2026-06-12-sector-prep`). But do not collapse a genuinely distinct, named artifact into the anchor just to avoid creating a page.
