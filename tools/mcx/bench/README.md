# mcx token-economy benchmark

The benchmark compares a native MCP call with an equivalent `mcx run` chain. Native calls return
the complete fixture payload to the model; chains process the same payload inside the sandbox and
emit only a digest.

## Metrics

Each scenario reports:

- **emit** — tokens sent by the model: native tool arguments versus the `mcx run` invocation.
- **recv** — tokens returned to the model: the source payload versus the digest.
- **context** — `emit + recv`, the amount retained in the context window.
- **mcx % of native** — `mcx context / native context`.

Token counts use `tiktoken` with `cl100k_base` through `count_tokens.py`.

## Run

```sh
ruby bench/bench.rb
```

The default run uses deterministic synthetic fixtures generated by `gen_fixtures.rb`. Synthetic
records use identifiers such as `PROJ-123`, `example.invalid`, and obvious placeholder UUIDs. To
benchmark another synthetic corpus, point `MCX_FIXTURES` at a caller-provided fixture directory:

```sh
MCX_FIXTURES=/path/to/synthetic-fixtures ruby bench/bench.rb
```

Every digest is produced through the normal executor path. `MCX_FORWARD_REPLAY` supplies an ordered
fixture queue to the baked `forward()` helper, so benchmark chains contain no alternate client or
benchmark-only result shaping.

## Interpreting the output

- Larger source payloads usually produce a smaller retained fraction because the digest stays
  bounded while the native response grows.
- Fan-out and cross-server joins show the clearest savings because intermediate payloads never
  enter model context.
- Compact JSON keeps comparisons stable. Pretty-printed server output would increase the native
  receive count without changing the chain's result.
- Compare scenarios by retained fraction, not by absolute token count, when fixture sizes differ.

## Pattern

Fan MCP calls out inside one sandbox run, compute the answer there, and return only the answer. Raw
issue bodies, page blocks, messages, and spreadsheet rows stay within the process that needs them.
