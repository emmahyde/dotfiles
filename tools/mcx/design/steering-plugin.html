mcx plugin — two-registry architecture

One plugin ships the mcx engine + hooks + skills + config. Two registries, split by capability: declarative filters that auto-filter every MCP call, and imperative chains the agent runs on purpose.

Hook lifecycle — where each layer plugs in

user prompt→ UserPromptSubmit · nudge → chain→ model plans→ mcx run <chain>·or· direct MCP call→ PostToolUse · mcx filter→ context

Chains are opt-in (a nudge steers the model onto them). Filters are automatic — the hook filters every configured tool's output with no model involvement.

Registry 1 · passive

Filters — filter

Declarative JSON reshaping applied to every call of a tool. No code, no forward, no sandbox.

enginenative Go (mcx filter --tool …) runtimenone — pure data transform forward()✗ appliedauto, in PostToolUse hook 
// filters.json — fixed declarative vocabulary
"mcp__jira__getJiraIssue": {
  "drop": ["expand","self","fields.renderedFields",
           "fields.changelog","fields.comment"],
  "rename": {"fields.assignee.displayName":"who"},
  "truncate": {"fields.description": 400}
},
"mcp__slack__slack_read_thread": {
  "maxTextChars": 4000   // prose → blunt cut
}
// no entry → pass through untouched (fail-open)
tool_response→ mcx filter→ updatedToolOutput

Supports keep (allowlist) and drop (denylist). Shipped defaults are drop-only cruft — can't hide signal. Reach past this vocabulary → it's a chain, not a filter.

Registry 2 · active

Chains — forward

Scripts that orchestrate MCP calls: sequential, cross-tool, parallel. Run deliberately; return a digest.

engineexecutor sandbox (mcx run <name>) runtimeruby / python / js / shell forward()✓ baked-in preamble appliedon purpose, model-invoked 
# baked env: forward() + emit() injected, no boilerplate
issues = args["keys"].map { |k|
  forward("jira", "getJiraIssue", {"issueIdOrKey" => k})
}
rows = issues.map { |i| {key: i["key"],
        status: i.dig("fields","status","name")} }
emit({count: rows.length, issues: rows})
# 5 payloads (~90k tok) fan out + die in the sandbox;
# only the digest (~200 tok) re-enters context
one mcx run→ N forwards→ emit digest

This is the existing register / list / run / remove registry (manifest.json). Skills + the UserPromptSubmit nudge steer the model here when a prompt implies a fan-out.

Plugin layout

mcx-plugin/ .claude-plugin/plugin.json hooks/hooks.json # UserPromptSubmit + PostToolUse scripts/ # mcx engine moves in here mcx (built binary) skills/ mcx/SKILL.md # /mcx quickstart + cheatsheet mcx-author/SKILL.md # write & register a chain filters.json # Registry 1 defaults chains/*.rb # Registry 2 example scripts

Who does what

PostToolUse hookshells to mcx filter; auto-applies a filter to every configured tool. No nudging. UserPromptSubmit hookfactual one-liner nudging a chain when the prompt implies a fan-out. skills/mcx cheatsheet; mcx-author teaches writing + registering a chain. mcx (Go)owns both registries: filter reads filters.json; run executes chains.

Filters need no steering — they just happen. All steering effort goes toward getting the model onto chains for multi-call work.
