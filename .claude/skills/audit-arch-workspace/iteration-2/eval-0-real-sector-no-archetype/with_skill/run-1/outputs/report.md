# /audit-arch — Sector (whole repo, no archetype argument)

Run by: Claude Fable 5 (skill author), 2026-07-20. Evidence gathered via three read-only exploration dispatches plus code-graph metrics (god-class, coupling, circular-dependency) and targeted spot-reads. Revised same day per Emma's direction: an in-repo roadmap diagnosis is corroboration, not remediation, so the piloting↔node-graph split is promoted to Finding 1 and the bus-bridge finding drops to the cut line.

> Auditing as: **Resident senior engineer** (no archetype argument). Fitness bar: a single-process, single-player MonoGame desktop game — a headless C# simulation engine (`Sector.Engine/`) plus a presentation frontend (`Sector/`) — judged on idiomatic fitness for what it demonstrably does today, plus the project's own declared claims: "Pure C# simulation — no engine dependencies, fully testable headless" (README.md:31), "All state changes go through EventBus" (README.md:192), and strict one-way engine/presentation layering (Sector.Engine/CLAUDE.md). Ethos (docs/design/WORLD_SIM_ETHOS.md, docs/design/PILLARS.md): *"a working ship in a world that doesn't wait for you"* — pillars Weight, Persistence, Proximity, Legibility; the world must keep moving offscreen and its consequences must reach the player legibly. **Core subsystems:** the world simulation heartbeat (`Sector.Engine/World/Simulation/`), simulation time, persistence (save/load), the engine↔frontend boundary. **Supporting:** Crew, Events/narrative, Ship, economy surfacing, rendering. **Peripheral:** CLI tooling, ship-bake, debug bridge.

### 1. Two positional realities (piloting scene vs node graph) → one engine-owned world frame

**Where:** `Sector/App/View/Screens/Piloting/Scene.cs` (3,462 lines; ~15 scattered `CurrentNodeId` read sites, e.g. :337, :2245, :2959, :3220), `Sector/App/Piloting/EncounterSpawner.cs:172-258` (walks live `ALifeDirector.Agents`, maps each `SimAgent` to a local `EncounterActor`, interpolates local positions), `Sector/App/Piloting/PilotingStateProvider.cs` (652 lines, scene-owned mutable snapshot rebuilt every update), Piloting/CLAUDE.md ("`Obstacle.SectorPosition` is the single position authority" — an *app-layer* authority), corroborated by docs/design/WORLD_SIM_ETHOS.md §9's own diagnosis: "two games that share a save file."

**Current flow:** The engine's world is a discrete node graph (`SectorMap.CurrentNodeId`; `SimAgent.CurrentNodeId`/`DestinationNodeId`/`TravelProgress`). The piloting scene fabricates a continuous local space per node: free-flight spawn position is derived from `map.GetNode(map.CurrentNodeId)` plus a local offset (Scene.cs:337); ship, obstacle, and encounter positions are app-owned `Vector2`s; encounters are copied from the live `ALifeDirector.Agents` collection each scan with positions invented by local interpolation (EncounterSpawner.cs:229); and all continuous state is discarded on scene exit — never written back to the engine. The coordination mechanisms are shared-collection reads, one-way copies, and discards; the only return path is `SensorContactEvent` publishes (EncounterSpawner.cs:340).

**Conflict:** Duplicated source of truth for the fact the ethos cares about most — *where things are*. Every positional fact exists twice (graph coordinates and scene-local coordinates) with hand-written one-way sync, and neither representation is authoritative enough to persist (Finding 3's ship-position save hole is a direct symptom: there is no single position worth saving). The guard (documented cache with one owner) does not apply — neither side owns the fact. The repo's own ethos doc diagnosing this precisely (§9, with decisions D1–D7) is *corroborating evidence of centrality, not remediation*: the structure is still in force, and every new piloting-adjacent feature (encounters, mining, contacts, sensor logic) pays the dual-representation tax again, deepening the migration this doc already says must happen.

**Simpler architecture:** The worldframe the decision ledger already sketches, stated as a structure: one engine-owned continuous world frame into which node-graph positions project deterministically (D7: SimAgents stay graph-native; the projection is derived, not stored), with the scene as a renderer/interpolator that owns zero positions (D1: continuous sim, streamed presentation; D6: presentation-only transitions). Named touchpoints: `EncounterSpawner` becomes a projection reader, Scene.cs's spawn/position code reads the frame, `PilotingStateProvider` carries frame-derived snapshots, and `ShipSaveData`'s dead position fields (Finding 3) gain a real writer.

**Deletion test:** `EncounterSpawner`'s SimAgent→EncounterActor mapping and `InterpolateAgentPosition`; the ~15 scattered `CurrentNodeId` equality checks in Scene.cs; the discard-on-scene-exit semantics (position becomes a persistable fact, closing part of Finding 3); the entire bug class "the scene disagrees with the sim about who is nearby" — which is pillar P3 (Proximity) failing at the structural level, not the tuning level.

**Cost honesty:** The largest migration in this report — it *is* the worldframe spike, and the team has already sized it as spike-worthy. What the audit adds is ranking, not novelty: this should outrank further micro-fidelity investment because each new piloting feature built on the dual representation raises the migration's cost. Risks: flight-feel regressions (local physics is currently tuned in scene space), save-format changes, and the temptation to do it wholesale — D1–D7 define the bounded path; hold to it.

### 2. Presentation-owned world heartbeat → engine-owned tick scheduler

**Where:** `Sector/App/SessionState.cs:3929-4015` (`TickSimulation`), `SessionState.cs:283-299` (engine managers constructed inside the frontend), `Sector.Engine/World/Simulation/WorldSimulation.cs:173-210` (`Tick`), `Sector.Cli/LivePlaySession.cs:~182-184` (second, divergent tick host), `Sector.Engine/Core/Tick/TickInterfaces.cs` (existing tick abstractions, unused by the orchestration).

**Current flow:** RootScreen drains a 1-second accumulator into `SessionState.TickSimulation` (RootScreen.cs:376-386). That method — in the MonoGame frontend — is the world's actual heartbeat: it direct-calls `WorldSimulation.Tick`, then separately ticks `PlayerShip`, activity manager, storylet/situation selectors, intel decay, and `MiningRushManager`, then on day boundaries direct-calls ten more `ProcessDay` methods (character sim, drift, court, nutrition, price speculation, mining contracts, faction heat decay, ledger pressure). `PriceSpeculationManager` and `MiningRushManager` are not merely ticked from the app — they are *constructed* in SessionState (SessionState.cs:283, confirmed as the only production `new PriceSpeculationManager` site), invisible to the engine's own wiring. A second host, `Sector.Cli/LivePlaySession.cs`, reassembles a different, smaller notion of "a tick" by hand. Meanwhile the engine contains managers that are constructed but ticked by nobody: `StationCivicManager` has no Tick method at all (event-reactive only, by design or omission), and `FactionAI.Tick` is reachable only from tests (repo-wide grep excluding tests: zero production call sites). SessionState itself is the repo's largest file (5,525 lines, 211 methods, 69 fields, 112 referencing files) and contains genuine domain logic — shore-leave resolution with personality-to-action matching (:648-800), a travel/fuel state machine with a low-fuel one-shot warning (:1080-1144), maintenance-recommendation prioritization (:836-895).

**Conflict:** God orchestrator. The guard — "a thin composition root that only wires" — does not save it: it constructs, wires, ticks, *and* implements domain rules, and every new engine system (price speculation, mining rush, nutrition, drift) has landed another tick line and another private field here. The deeper structural cost is that the ethos claim "the world doesn't wait for you" is architecturally inverted: the world cannot advance a single hour without the MonoGame presentation layer, and the engine's own README-claimed headless completeness is false in practice — a headless host must re-derive the secret tick liturgy (as LivePlaySession already does, differently).

**Simpler architecture:** Move tick composition into the engine. One engine-side scheduler (a `SimulationLoop` owned by `EngineContext` or `WorldSimulation`) with which every manager registers at construction — the idiomatic .NET shape here is exactly the registration pattern the codebase already half-owns (`Core/Tick/TickInterfaces.cs` defines `ITickService`/`IBudgetedTickService` for LOD scheduling; the same seam generalizes). Hosts — SessionState, the CLI, tests — call one method: `engine.Advance(deltaSeconds)`. Day-boundary fan-out becomes the scheduler's job (it already publishes `DayAdvancedEvent`; subscribers replace the hand-called ProcessDay list).

**Deletion test:** SessionState's ~90-line hand-maintained tick sequence and day-boundary cascade (:3929-4015); LivePlaySession's parallel tick assembly; SessionState's construction of engine managers (:283-299) and the private fields that exist only to tick them; the entire bug class "manager constructed but never ticked" (registration *is* ticking — StationCivicManager/FactionAI-style dead wiring becomes impossible silently); the frontend's knowledge of engine tick order.

**Cost honesty:** Touches SessionState, WorldSimulation, LivePlaySession, SimulationBootstrapper, and each registered manager (mechanical, per-manager). The real risk is tick-order semantics: today's order is implicit in SessionState's statement sequence, and some of it is load-bearing (e.g. supply-chain pressure before price reads). The migration must make ordering explicit (phases or priorities) rather than hoping alphabetical registration works. Domain logic extraction (shore leave, travel) is separable follow-up work, not a prerequisite.

### 3. Three parallel save-assembly paths → one save-participant registry

**Where:** `Sector.Engine/Core/Serialization/SavePipeline.cs:77-125` (16-pair extended registry; header comment at :3 still says "14 pairs"), `SaveData.cs:341-342` (`ShipSaveData.CurrentNodeId`/`DockedStationId` — declared, zero write sites), `Sector.Engine/Ship/ShipSerializer.cs:24-25` (writes only Id/Name/Fuel/FuelCapacity), `Sector/App/SimulationBootstrapper.cs:381` + `Sector/App/DefaultSectorBuilder.cs:246` (load path hardcodes `map.CurrentNodeId = n03.NodeId` — the same call as new-game), `SessionState.cs:2759-2776` (Captain Slice save bridge that only some paths call).

**Current flow:** Persistence is assembled by three coexisting mechanisms with different coverage: (a) the core `GameSaveData` DTO tree filled by `GameManager.AssembleGameSaveData`; (b) `SavePipeline`'s separately-maintained 16-pair manager↔DTO registry with a hand-written ordering constraint (PlayerKnowledgeManager requires NewsManager restored first); (c) a Captain-slice bridge living in SessionState that the mid-game save path does not call and the new-game snapshot deliberately omits. Facts fall through the seams: the player ship's position fields exist in the DTO but are never written by anyone, and on load `SimulationBootstrapper.CreateFromSaveData` rebuilds the sector map with the identical hardcoded-start-node builder the new-game path uses — so the saved game's position is unconditionally overwritten with `n03` regardless of where the ship was.

**Conflict:** Duplicated source of truth — three assemblers each believe they know what "the save" is, and none owns the whole fact. The don't-flag guard (a documented cache with one owner and invalidation) does not apply: coverage differs per path, the "14 pairs" comment is already stale against its own table, and nothing enforces that a new persistent system joins any of the three.

**Simpler architecture:** A single save-participant registry — the idiomatic C# shape is the one SavePipeline already is, promoted to be the *only* mechanism: every persistent system registers a named slice (populate/restore + declared restore-order dependencies), and both save assembly and load restoration iterate that registry, in the new-game, mid-game, and CLI paths alike. Position and docked-station become a slice like everything else.

**Deletion test:** The captain-slice special-case bridge and its "which path calls me" ambiguity; the divergence between `GameStartSnapshot.ToSaveData` and `AssembleGameSaveData`; the dead-but-declared `ShipSaveData` position fields (they get real writers, and the hardcoded `n03` reset on load disappears); the comment-enforced restore ordering (replaced by declared dependencies); the entire bug class "system X silently never joined the save," which pillar P2 (Persistence — *"consequences survive across sessions"*) is directly hostage to.

**Cost honesty:** Touches SavePipeline, GameManager, SessionState, SimulationBootstrapper, ShipSerializer, and requires a save-format migration story for existing saves (even if it's just "version bump, old saves keep the legacy loader for a release"). Making restore-order dependencies explicit may surface latent order bugs that the current comment-ordering happened to mask. This finding intersects the in-progress Flecs authority migration (one save authority is that migration's stated end-state) — the registry should be designed as the meeting point, not a competitor.

### 4. Four independent day/time accumulators → one owned simulation clock

**Where:** `SessionState.cs:117` (`_gameDay`, int, incremented on travel completion at :4191), `SessionState.cs:3931-3936` (`_gameClockDays` float + `_periodicAccumulatorDays` float, both advanced per frame), `WorldSimulation.cs:21,184-189` (`_dayTimer`, a fourth accumulator resetting at 24h), `WorldSimulation.cs:95-97` (`CurrentDayProvider = () => 0f` with TODO "wire from the SimulationClock owner"), `SessionState.cs:1114-1115` (travel tick time base stubbed to `0f` with TODO), `Sector.Engine/Core/SimulationClock.cs` (a complete value-type clock — with zero production owners; its only engine reference is that TODO comment).

**Current flow:** "What day is it" is answered by four accumulators that never read each other: an int day counter advanced by travel completion, a float clock advanced per frame, a separate periodic accumulator that actually fires `DayAdvancedEvent`, and an engine-internal 24-hour timer that triggers market/stock daily processing on its own beat. Systems needing the day either receive it as a parameter from whichever counter their caller happened to hold, or read `GameManager.Instance.DaysPassed` (a fifth derivation, used inside PlayerKnowledgeManager.cs:223), or get the stub `() => 0f`. All second→hour→day conversions are inlined at each call site; `SecondsPerGameDay` is a private constant of SessionState. Meanwhile `SimulationClock` — the exact abstraction this needs — exists in `Core/`, is listed in the engine's own CLAUDE.md namespace table, and is owned by nothing.

**Conflict:** Duplicated source of truth, compounded by framework-fought-not-used (the idiomatic fix is already written and stranded). No guard applies: none of the four accumulators is a documented cache of another; they are independent derivations from the same frame delta that can and do diverge (int vs float, travel-driven vs frame-driven vs threshold-driven), and two TODO stubs are live admissions that time has no owner.

**Simpler architecture:** One engine-owned clock instance — `SimulationClock`, given an owner (naturally the Finding-2 scheduler, but this finding stands alone) — advanced in exactly one place, publishing the existing `DayAdvancedEvent` on boundaries. Everything else reads `clock.CurrentDay`/hours or subscribes. `CurrentDayProvider` becomes a real reference instead of a stub.

**Deletion test:** Three of the four accumulators plus their drift potential; every inline `* 3600f` / `SecondsPerGameDay` conversion at call sites; the two `0f` TODO stubs; the `GameManager.DaysPassed` side-channel as a time source; the class of bugs where day-keyed systems (price history, intel decay, news aging, contract deadlines) disagree about the current day — which strikes directly at pillar P2/Weight, since offscreen consequence timing *is* the product.

**Cost honesty:** Touches SessionState, WorldSimulation, ShortageJobEmitter wiring, and travel logic. One genuine design decision is currently hidden in the duplication and must be made explicit: `_gameDay` advances on travel completion (a deliberate-looking pacing rule), while `_gameClockDays` advances continuously — unification forces the team to decide which rule is the game's actual calendar, and that is a design conversation, not a refactor.

### 5. Static singletons as the inter-manager API → context-injected references

**Where:** `Sector.Engine/Core/GameManager.cs` (fan-in: coupled to 680 files, the repo's #1 hub per the dependency graph), `WorldSimulation.cs:218-226` (`MarketManager.Instance.GetMarketAtStation(...)` reach-around in `UpdateAllMarketPrices`), `WorldSimulation.cs:162` (the same singleton captured in a `ShortageJobEmitter` closure), `WorldSimulation.cs:141` + `SessionState.cs:1170` (`PlayerKnowledgeManager.Instance`), `Sector.Engine/Core/Events.cs:18` (static `EventBus`) with `Core/Events/IEventBus.cs:47-90` (`EventBusProvider`/`DefaultEventBus` — an injection shim already built to work around the static). Dependency-graph evidence: the engine's Core, Crew, Events, Mining, World, and Ship directories collapse into a single strongly-connected cycle — there are no separable layers inside `Sector.Engine` today.

**Current flow:** Managers coordinate across module boundaries by reaching for static `.Instance` properties and the static bus rather than through references they were given. The traced consequences are concrete: the whole engine is one dependency cycle (nothing inside it can be built, reasoned about, or tested truly standalone); `GameManager` couples to 680 files; and lifecycle bugs of exactly this shape have already shipped — the recent `MarketManager.AttachFlecs` backfill bug (fixed in commit 72f2e117) was a singleton whose registration timing silently broke `GetMarketAtStation` for every consumer listed above.

**Conflict:** Shared-mutable-state-as-API via singleton reach-around. **Dimension and signal (Prohibition 1):** testability and headless modularity — signaled by the project's own claims: "fully testable headless" (README.md:31), the existing `TestEventBus`/`EventBusProvider` shim (built precisely because the static bus fights tests), and the one-way-layering constraint in Sector.Engine/CLAUDE.md. The guard (deliberate blackboard with a single owner) does not apply — these are ad-hoc global lookups, not a designed blackboard; the codebase's *actual* designed blackboard (the shared Flecs world via `EntityRegistry`) already exists and is documented.

**Simpler architecture:** Pass what you use. `EngineContext` already exists and already aggregates the managers; the idiomatic shape is constructor (or `Attach`-style, matching the codebase's own documented convention) injection of the two or three references each manager actually touches, with `SimulationBootstrapper` — already the documented single wire point — doing the handing. No DI framework; just fields instead of `.Instance`.

**Deletion test:** `MarketManager.Instance`, `PlayerKnowledgeManager.Instance` and their initialization-order hazards (the AttachFlecs-backfill bug class); the `EventBusProvider` indirection shim once the bus is a passed reference; the engine-wide strongly-connected cycle breaks into actual layers (Core ← World ← integration), making "headless, fully testable" true at the module level rather than only at the whole-engine level.

**Cost honesty:** The widest touch in this report — hundreds of mechanical call-site edits — and only worth doing incrementally, one singleton at a time, starting with the two that have already caused or hosted bugs (MarketManager, PlayerKnowledgeManager). `GameManager.Instance` itself is the long tail and may never fully disappear; the win is stopping *new* reach-arounds and de-cycling World/Simulation, not a purity crusade. Per-manager migration is compatible with the Flecs strangler-fig pattern the team already runs.

***

**Fitness bar used:** Single-process, single-player desktop simulation game; idiomatic C#/.NET for what the code does today; held additionally to its own declared claims — headless fully-testable engine, EventBus as the state-change spine, one-way engine/presentation layering — and its own ethos: a world that keeps moving without the player (Weight, Persistence, Proximity, Legibility). No scaling, multiplayer, portability, or extensibility dimension was signaled, and none was audited.

**Explicitly not flagged:**
- **The EventBus↔SignalBus hand-duplicated bridge and GameManager's dual-fire** (`SimulationBootstrapper.cs:323-332` copy-pasted at `:810-820`; `GameManager.cs:60-82` publishing `GameStateChangedEvent` *and* firing a native `OnStateChanged`) — a real duplicated-coordination conflict, dropped by the top-5 cut as the lowest leverage × centrality of the six candidates. The fix is small (one declared bridge component on the `SituationNewsBridge` pattern; one announcement channel) and rides along naturally with Finding 2's bootstrapper work.
- **Per-frame polling and Draw-path allocations in the piloting HUD** (`ShipStats.Draw` re-deriving state and interpolating strings each frame, `PilotingStateProvider` rebuilt every scene update) — the poll *is* the domain in a game render loop, and no frame-budget ambition or performance complaint is signaled anywhere in the docs. Under a `/audit-arch frame-budget` archetype these become findings; under this bar they are not.
- **The dict+Flecs dual-store duality** across ~22 managers — a generic audit's "two sources of truth!" headline, excused here because it is a documented, in-progress strangler-fig migration with a stated end-state, a gold-reference manager, and a single wire point (Sector.Engine/CLAUDE.md "ECS" section). Flagging a migration for being mid-migration is noise; Finding 3's save-registry proposal is designed to converge with it, not fight it. (Contrast with Finding 1: the Flecs migration is excused because it is demonstrably *executing* — flipped managers, a gold reference, a single wire point — whereas a diagnosis that exists only as a decision ledger is corroboration, not remediation.)
